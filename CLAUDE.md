# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Declared in `pyproject.toml` (`[project.dependencies]`, dev extras under `[project.optional-dependencies]`). The `requirements/*.txt` files are gone.
- **The tool is CLI-first, installed from PyPI** — `uvx openoutreach find 10` / `pip install openoutreach`, entry point `openoutreach/__main__.py:main`. **Docker is the server deploy only** (`docs/infrastructure.md` §7 in `openoutreach-docs`); development and tests run natively. See the cards `p1-e2-cli-entry-points` and `p1-e1-find-verb-bounded-goals`.
- **`pip install openoutreach[send]` adds the sender.** The `send` extra pulls the separate `openoutsend` distribution ([OpenOutSend](https://github.com/eracle/OpenOutSend)) so one install puts both `openoutreach` and `outsend` on the PATH and `openoutreach find 50 --json | outsend` works. **It is a packaging alias and nothing more** — separate repo, package, database and process. **Nothing under `openoutreach/` may import `openoutsend`**: the boundary is a pipe, our own sender gets no privileged path, and an import would be exactly the coupling the CSV/JSON contract exists to refuse. See the `openoutreach-docs` card `p1-e2-find-send-boundary-contract`.
- **There is no daemon.** The work verb is bounded by a goal: `find N [emails]` runs until it has that many *more*, prints the whole campaign as CSV on stdout, and exits — 0 only if the goal was met. Do not reintroduce an unbounded loop, a job-level timeout, or a file the tool writes for the operator; each of those was tried and each was a workaround for a process that never ended. See the card `p1-e1-find-verb-bounded-goals`.
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes. **The CLI's contract has a fourth reader** — `skills/find-leads/SKILL.md`, the Claude Code plugin shipped from this repo (`.claude-plugin/plugin.json` + `marketplace.json`, so `/plugin marketplace add eracle/OpenOutreach` installs it). It restates the verbs, the flags, which of them can spend, the export columns and the `ErrorType` vocabulary, so a change to any of those has to land there too or the skill teaches a CLI that no longer exists. `claude plugin validate .claude-plugin/plugin.json` checks the manifests.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules.
- **Migrations**: one `0001_initial` per app and no history before it — see *The cut* below. Existing installs upgrade cleanly **from that point on**; a DB created before it cannot upgrade past it, by decision. During a multi-file change, let the models settle first — generate migrations in one pass at the end of the sweep, then run the suite. Don't hand-write a migration mid-change.

## Project Overview

OpenOutreach — a self-hosted **lead finder that qualifies for you**, with **zero platform-ToS surface** (browserless; no social-network account, no scraping):

**define ICP → discover → qualify → rank → (optionally) resolve an address → export CSV.**

- **Discovery** is a licensed source — BetterContact **Lead Finder** (ICP search returns firmographic profiles, no emails, billed nothing). The walk over its keyword index is *counting*, not a model.
- **Qualification** is the crown jewel — per-campaign **GPR + BALD active learning** over 384-dim embeddings, decided by an LLM, which also **writes down why**. That reason is the product.
- **Enrichment** is the one paid step — a **finder** resolves a work email for the top-ranked leads only (one credit per verified hit), fronted by a free cross-operator cache (the hub). Optional: a lead with no address still exports. **The resolver sits behind a seam** (`enrichment/provider.py`), which picks a finder from whichever key is configured: BetterContact (async waterfall) or Apollo (synchronous `people/match`, 0 credits on a miss). **Only the resolver leg is interchangeable** — discovery is BetterContact's Lead Finder and nothing else, so an Apollo-only install can enrich but cannot find. **Apollo is wired but deliberately unexposed**: undocumented key, no wizard step, never run against a live account. `enrichment/apollo.py`'s docstring lists what to verify before exposing it.
- **The output is the command's own stdout.** `openoutreach find 10 emails > leads.csv` prints the **whole campaign** in the column names Instantly and Smartlead already read, so the newest file supersedes every earlier one. No export command, and no file the tool manages. See *The lead export* below.

Django + Django Admin own the CRM/ORM (models are this project's); pydantic-ai drives the LLM calls.

### The cut (2026-08-19) — this project does not send email

The sending half was **ported to [OpenOutSend](https://github.com/eracle/OpenOutSend)**
(parked under `cold_outreach/` there, with a README mapping every dangling dependency). Gone from
here: the `emails` app entirely — `Mailbox`, SMTP/IMAP, the mail log (`Thread`/`Message`/
`DeliveryEvent`/`FolderCoverage`), the sender, the three send guards (hours/rate/volume), the
opt-out mechanisms — plus the outreach agent, `core/sending_window.py`, the `chat` and `legacy`
migration anchors, and the **freemium promo campaign** with its `KitQualifier` and HuggingFace kit.

Four consequences worth knowing before changing anything:

1. **Nothing gates a free step on a paid one.** Discovery and qualification are ungated; the old rule (*never qualify a lead there is no room to email today*) was the single line that made a mailbox-less install silently produce nothing. Don't reintroduce that shape.
2. **The opt-out duty left with the code.** A finder that contacts nobody is not the sender under CAN-SPAM/GDPR/CASL. `Lead.disqualified` survives as the export's exclusion filter, but nothing sets it automatically any more. The hub store's own suppression is separate and unaffected.
3. **The GP never trained on a market signal.** `get_labeled_arrays` reads the LLM's fit verdict alone, so losing replies and bounces cost the model nothing.
4. **A pre-cut database cannot come forward.** The migration history was squashed, not migrated, so an install created before the cut has to stay on the tag `pre-finder-cut`; pulling `main` onto one leaves a DB that cannot migrate and a process that will not start. No such install is running any more — the two that were died with the old prod VM (2026-08-20) — so this is a constraint on anyone's old copy, not on ours.

## Commands

```bash
# Installed (what an operator runs)
uvx openoutreach find 10 > leads.csv   # ten more qualified leads, then exit
openoutreach find 10 --emails          # ...and buy an address for whatever is ready
openoutreach find 10 emails            # ...carrying an address; one credit each
openoutreach find 0                    # no work — print what the campaign already has
openoutreach status                    # what is configured, blocked and counted

# Local dev
make setup    # install -e ".[dev]" + migrate + bootstrap CRM
make find N=10 [UNIT=emails]   # == python manage.py find 10 emails

# Testing (native — there is no docker-test)
make test
.venv/bin/pytest tests/test_qualify.py   # single file
.venv/bin/pytest -k test_name            # single test

# Docker — the server deploy only
make build / make up / make stop / make logs
```

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `openoutreach/__main__.py:main` — the `openoutreach` console script, and the one entry point; it strips the global `--db` flag before Django's per-command parsing. A bare invocation prints the command list — it used to default to `run`, and with the work verb bounded there is nothing sensible to default *to*, since `find` needs a number and choosing one would spend the operator's credits on a guess. `manage.py` is a thin shim over it for work inside a checkout. **Three verbs, chosen rather than accumulated**: `init [--product-docs F] [--target F] [--name N] [--json]` · `find N [emails] [--emails] [--campaign] [--new] [--json] [--batch] [--open] [--debug]` · `status [--json]`. **`reset` was deleted 2026-08-21 to keep the surface lean** — everything an install writes hangs off `settings.state_dir()`, so `rm -rf ~/.openoutreach` plus a `find` is the reset and configuration comes back from the environment. The real cost: the ICP seed only runs for a campaign with **no** query nodes, so there is no longer a way to re-seed a walk while keeping its leads and verdicts. **`--campaign` is optional and stays that way** — `_select_campaign` takes the only campaign when there is one and raises a `bad_config` listing them all when there are several; ambiguity is an error, never a guess. **Spending is opt-in at every layer** (2026-08-21): `buy_addresses` defaults to `False` in `run_job` and `run_one_action`, `--emails` turns it on, and the `emails` unit implies it — the noun says what to *count*, the flag says what may be *paid for*. It used to be the other way round (`--no-emails` to opt out), so a run counting leads quietly bought addresses for whatever an earlier run left past the confidence gate; a flag you forget should cost a feature, never money. `--debug` is the shorthand for `--log-level debug` (same dest, so they cannot disagree). **Neither the CSV nor the daemon is a verb** — `export_leads` was deleted when the run started writing the file itself, and then the file went too when `run` became `find` and the rows became its stdout. `setup_crm` lost its verb — it was an implementation detail, and `find` calls the function; `reset_data` and then `reset` itself went the same way. **`--json` belongs on every verb with a result**: `init`, `find` and `status`, which is all of them — and **a failure answers in the caller's format too**, so `--json` turns the `error:` line into `{"error": {"type", "message"}}`, still on stderr (stdout stays result-only, or `find --json > leads.json` would collect an error object). The `find` command (`core/management/commands/find.py`) does: migrate → CRM bootstrap → onboard if incomplete → validate → select the campaign → `run_job` → print. **Onboarding** (`core/onboarding.py`) is interactive, **four steps** — `campaign` (product/objective) → `llm` (live-verified) → `bettercontact` (mandatory — the key powers *both* discovery and enrichment, so the barrier is an account, not a bill) → `account` (your email, country, newsletter, legal acceptance, in one step). The `account` step's address is the human's own inbox, stored as `User.email`, the newsletter target and the contacts-store key. Built as an ordered list of idempotent `Step`s (`is_done`/`run`/`from_env`, persist-as-you-go) that resume where they left off; prompt primitives vendored in `onboarding_wizard.py`. **The environment is the second way in, and the only one an agent has**: every field is settable as `OPENOUTREACH_*` (`PRODUCT_DESCRIPTION`, `CAMPAIGN_TARGET`, `AI_MODEL`, `LLM_API_KEY`, `LLM_API_BASE`, `BETTERCONTACT_API_KEY`, `OPERATOR_EMAIL`, `COUNTRY`, `ACCEPT_LEGAL_NOTICE`, `NEWSLETTER`, `CAMPAIGN_NAME`), and boot is **hydrate → re-check `missing_keys()` → wizard on a TTY, else exit naming the variables that would have satisfied it**. Three rules hold that path honest: a step hydrates only when it has *all* its own fields (no half-applied step); a set-but-invalid value raises `OnboardingEnvError` instead of falling through to "missing"; and **legal acceptance is never inferred** — `ACCEPT_LEGAL_NOTICE` must say yes, and `NEWSLETTER` defaults **off everywhere** because silence in a config file is not consent. The LLM key is live-verified on this path too, since headless there is nobody to re-ask. *(The `mailbox` and `signature` steps went with the sending leg — that was most of the install path, and behind the mailbox step stood the disclosure that the tool would send the maintainer's promo campaign from the operator's own mailbox.)*
- **The run's narrative**: what `find` prints on stderr while it works **is** the product surface, and it follows a script written down first — `openoutreach-docs/docs/first-run-design.md` §6. **Two levels, and nothing is deleted between them**: INFO is addressed to the operator (every line answers a question they would ask), DEBUG carries *everything INFO ever said plus the engine's own reasoning* — the posterior behind the spend gate, the frontier/retirements/page offsets, the machine discovery seed, the anchor top-up, and the cycle's per-row decisions and timings. A line that stops being operator-facing is **demoted, never removed**. **The GP's acquisition strategy and class counts moved the other way, to INFO** (`qualify.run_qualification`, `top_up._advance`) — *which regime picked this candidate and why* (`cold phase`, `exploit (p)`, `explore (BALD)`, with the neg/pos count that decided it) is a question an operator watching the run asks, not just the engine reasoning about itself. The beats: minute 0 states campaign + goal + whether the run may spend (`find._announce_the_run`); the **ICP echo** prints the synthetic ideal profiles as *"Looking for people like:"* (`icp.log_icp_echo` — already computed, previously shown only as a count, and the earliest chance to notice the product description was misread; a first run has none until the job writes them); **both verdicts are printed** with their reason, `✗` against `✓` (`qualify._verdict_line` — watching it turn people down is what makes the acceptances credible, and `logblock.step_line`'s fixed-width label column is the wrong primitive for a person's name); progress counts **toward the goal the operator typed** with `★ first lead · 52s` as its own milestone (`job._log_progress`, `JobResult.elapsed` — reported, never enforced; there is still no timeout); and the gate that is actually holding is named with **every consequence it has** (`cycle.pipeline_summary` — the finder key is one key doing two jobs, so losing it stops discovery *and* the paid lookup while leaving the free address sources; `buy_addresses` is passed in because *addresses not requested* is the gate most likely to be holding on a bare `find`). `logblock.py`'s grammar was **not** replaced — the redesign happened inside it.
- **The output contract**: `core/management/base.py:OpenOutreachCommand` + `core/errors.py`. **stdout is result-only** — logs, the banner and Django's own `migrate` narration all go to **stderr** (`core/logging.py`, and `core/management/bootstrap.py:ensure_database` passes `stdout=stderr` into `call_command("migrate")`), so a redirected stdout yields data and nothing else. **An expected failure is one line**: `error: <type>: <message>` on stderr + exit 1, `type` from `ErrorType`, and *no traceback* — a rejected key is an answer, not a bug (an unexpected exception still raises). `OpenOutreachError` deliberately does **not** subclass `CommandError`, because Django prefixes that with the class name and would put noise in front of the line an agent parses. Provider refusals are typed at the HTTP boundary: 401 → `provider_auth`, 402 → `provider_out_of_credits`, exhausted 429 backoff → `provider_rate_limited`. **The 429 backoff is `urllib3.Retry` mounted on the session** (`bettercontact._RETRY`: 5 attempts, `backoff_factor=5` doubling, `backoff_max=120`, `respect_retry_after_header`, and **only** 429 in the forcelist — a 401/402 is final and retrying it is noise). Hand-rolling that loop, or bending `tenacity` (which retries on exceptions, not statuses) into the shape, would both be worse copies of what the HTTP stack already does.
- **`status`**: `core/status.py` (builds one dict, reads only) + `core/management/commands/status.py` (renders it — human by default, `--json` for a program). **`find` ends with the same `next_action`**, read once from `build_status()` after the work and rendered by `status.render_next_action` — on stderr beside the counts, or as a `next_action` key under `--json`. That is what makes a run stopping with ranked leads and an empty wallet say so, at the one moment it can. The renderer lives in `core/status.py` rather than in the command because two callers print the sentence and it must have one spelling; the arithmetic is derived once and **not** carried through the run — two earlier attempts put the balance read and a deal count in `core/job.py` (an HTTP call to a payment provider inside the bounded-goal loop) and in `enrichment/lookup.py` (per-deal, so *read once* needed module-level mutable state). The standing state of the database, for a reader who did not run the job: what is configured, what is **blocked and why** (stable strings from `core/errors.py`), the counts, the credit balance, and `next_action`. **It is smaller than it was, on purpose** — it began as the verb an agent asked *instead of tailing a log*, because a daemon could not answer for itself; with `find` returning its own result, that job is gone. Three things it gets right on purpose: **a balance that could not be read is not a balance of zero** (`no_credential` / `provider_auth` / `provider_unavailable` are reported as *why*, so a rejected key never renders like an empty run); **`exportable` is not `mailable`** — the export excludes only the two rejections, so a `QUALIFIED` lead exports with a blank `email`, and the counts split `exportable_with_email` / `exportable_without_email` from the records themselves rather than from a state standing in for them; and **`next_action` is ordered by what blocks progress** — `add_credits` sits above `print_leads` because a ranked lead cannot advance without credits, and `ranked_for_lookup > 0` is itself the proof that value exists, so the *never before value* rule holds without a special case (a campaign with nothing qualified gets `find_leads`, which costs nothing). The balance is `GET /api/v2/account` → `credits_left` (`bettercontact.credit_balance`, `X-API-Key`).
- **State machine**: `crm/models/deal.py:DealState` — `QUALIFIED → READY_TO_FIND_EMAIL → FINDING_EMAIL → RESOLVED`, with `NO_EMAIL_FOUND` and `FAILED` as the other terminals. **Every state below `RESOLVED` is terminal**, and `QUALIFIED` is already exportable: an address is an enrichment on top, never a precondition. The GP confidence gate promotes `QUALIFIED → READY_TO_FIND_EMAIL` (rationing the paid lookup — a **spend** gate and nothing else, never a quality score). The paid lookup runs **whichever finder `provider.active()` names**, and the transport is the provider's own: `buy_address` resolves free-hub-first (hit → `RESOLVED` directly), then calls `start`, which either returns a **terminated** outcome (a synchronous finder like Apollo — straight to `RESOLVED`/`NO_EMAIL_FOUND`, never entering `FINDING_EMAIL`) or a **handle** (BetterContact's async job — park at `FINDING_EMAIL`); `check_lookup` then polls the job's `request_id` — hit → `RESOLVED`, miss → `NO_EMAIL_FOUND` (its own terminal, **no reason and blank outcome** — the lead was an LLM fit positive and only *reachability* failed, so the ML labeler keeps it at label=1), couldn't-run → back to `READY_TO_FIND_EMAIL`. **A still-running job is never abandoned**: there is no deadline and no attempt limit, the step just doubles `not_before` on the same `request_id`. The deadline used to revert the deal instead, which put it back in the pool for a *second* paid job — a hot resubmit loop that turned a provider outage into 418 submits and 4,512 polls in a week for ~40 leads, none terminating. Doubling makes waiting cheap (a week = 17 polls) and refuses to mislabel a provider outage as an unreachable lead. `COLLECT_BACKOFF_MAX_S` (a month) rails the *interval* only, so `datetime` can still represent the schedule. The job handle + poll backoff live **on the deal** (`lookup_request_id`, `lookup_attempt`, `not_before`), so the wait gates that one row. `Outcome` is down to `wrong_fit`/`unknown`; `Lead.disqualified=True` = permanent account-level exclusion (a **different column** from `FAILED` — the export filters both); LLM rejections = `FAILED` + `wrong_fit` (campaign-scoped). *(Two legs have been removed: the connect leg with the browser channel, and the send leg — `READY_TO_EMAIL`/`EMAILED`/`COMPLETED`/`UNSUBSCRIBED` plus the reply outcomes — with `emails/*`. Dropping the reply outcomes also retired a live mislabelling: the reply step moved a deal to `COMPLETED`, not `FAILED`, so a "not interested" reply trained the GP as a **positive**.)*
- **The job**: `core/job.py`. `Goal(count, unit)` where the count is a **delta** — "ten more than you had" — and the loop is four lines: `while produced < goal: if not run_one_action(campaign): break`. **No timeout, by decision**: every unit of work already carries its own bound (`deal.not_before`, the doubling lookup backoff, `urllib3.Retry`), so a job-level clock would answer the same question worse — it knows nothing about *why* the run is waiting. The terminal condition is real state: *nothing can advance right now*. **Progress is a set, not a subtraction**, so a lead rejected mid-run cannot cancel out one that was found, and `--new` stays exact for `emails` (whose goal is usually met by leads that were already exportable and merely gained an address). Stopping short is `goal_unreached` — including `Ctrl-C`, the operator's own deadline for the one unbounded case, a campaign whose leads are all rejected — or `bad_config` from `HALTING_ERRORS`. **Exit 0 means the goal was met and nothing else**; the rows print either way, so *the code says how much you got and the type says why it stopped*.
- **The cycle**: `core/cycle.py`, which owns the hierarchy and **no loop at all**. **A queue is a status, not a table** — work is found by asking the deals what they need, so nothing is minted and no row's timestamp can gate another. One action per call, with **no periodic side-effects** (the mail pass and the daily warmth re-measure both left with the sending leg). `run_one_action` walks one ordered hierarchy and stops at the first thing it can do, so priority *is* that order: **1** `FINDING_EMAIL` → `check_lookup` (`not_before` elapsed), or `reclaim_lookup` → `READY_TO_FIND_EMAIL` when the deal carries no `lookup_request_id` — there is no job to poll and no credit was spent, and the row used to *skip* those, stranding them in a state nothing else claims (two deals, 206h) · **2** `QUALIFIED` → `promote_to_ready` · **3** `READY_TO_FIND_EMAIL` → `buy_address` (a provider is configured) · **4** the campaign itself → `top_up`. Unlisted states are terminal and cost nothing. Steps live in `enrichment/lookup.py` and `core/pipeline/top_up.py`; each takes one entity and returns the next `DealState` or `None`, and `cycle._apply` does one `deal.save()` so a transition and its audit fields commit together. Steps are **total** — the loop's `try/except` is a bug backstop, not a retry policy; a step that wants to wait writes `deal.not_before`, which is the only retry mechanism there is — and is what lets a job end honestly, since a row that waits stops being due. **Queued is not due**: `buy_address` on an unreachable provider backs the deal off rather than leaving it eligible, or the next pass re-picks the same one forever (noise under the daemon, an endless job now). `HALTING_ERRORS` (`ModelHTTPError`) ends the job with a typed line instead, or a bad LLM key would retry forever behind an `alive` line. **Rows 2 and 4 have no gate at all, and that is the pivot**: they used to share `room_to_send_today` (*never buy an address, and never spend an LLM call qualifying, for someone there is no room to email today*), which was right while every lead ended in a send and was also the single line that made a mailbox-less install produce **nothing** — zero pool headroom, comparison never true, discovery and qualification silently stopped. Nothing replaced it: discovery is free, qualification costs the operator's own LLM key, and what caps the paid step is the number the operator typed, since one credit is one verified address. **Do not reintroduce a gate on a free step derived from a paid or absent one.** **Campaigns no longer take turns** — `_rotate` is gone, because a job names its campaign and fairness has nobody to be fair between. **The hierarchy is data** (`ROWS`, name + function), so each action logs the row that fired and its duration, every row logs its decision time at `debug`, and when nothing fires `pipeline_summary` prints the counts — which is also the *reason* a job stopped short, since *no work* otherwise looks exactly like *work behind a gate*. *(Replaces the `Task` model, `core/scheduler.py`, `core/quota.py` and `core/session.py` — a token queue inherited from the Playwright era. On 2026-08-05 it slept 34 hours: two never-terminating polls had backed off 45h, were the only rows, and 55 ready deals had no token and so were not work.)*
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification, over 384-dim FastEmbed vectors cached on `Lead.embedding`. Per-campaign GP models in `Campaign.model_blob`. **It trains on the LLM's fit verdict and nothing else** (`get_labeled_arrays`: label 1 = any non-`FAILED` deal, 0 = `FAILED` + `wrong_fit`) — no market signal was ever in that loop, which is why handing sending away cost the model nothing. The correction loop is the human: read `reason`, edit the product description and the ICP.
- **Discovery + enrichment**: `openoutreach/discovery.py` (Lead Finder `search`, free) uses the blocking `submit_and_poll` transport; `enrichment/bettercontact.py` (paid finder) splits it into `submit(query) → request_id` + `poll_once(request_id) → PollOutcome` so a run never blocks on a poll (`check_lookup` owns the backoff, on the deal's own `not_before`). **Discovery is one counted, add-only walk over keyword sets** — from first principles: Lead Finder is a *keyword index*, not a facet store (words inside one string AND, strings inside one list OR, field vs field AND), so the atom is a **single word**. A **node** is a set of `(field, token)` `Keyword` rows; its children are itself plus one more token, capped at `select.MAX_TOKENS_PER_FIELD` (2) per field — the words in one field are ANDed inside it, so a third makes a title nobody holds; there is no remove move, because the frontier is global — every unfired child of every fired node in one pool — so a shallow node's untried siblings stay reachable without one. `discovery.filters_for(keywords, headcount)` is the only place a node becomes provider JSON: same-field tokens are **space-joined** (the narrowing move, and the generator of the best queries measured — `"founder cto"` counts 9,027 at near-perfect precision), different fields are separate keys, and the include-list OR is deliberately **unused** (a union reaches one ~10k window where the same values as separate queries reach one each). Axes are `lead_job_title` / `lead_seniority` / `lead_location`; `lead_industry` is **inert** (a nonsense value returns the identical count), `lead_function` is `lead_department` under a second name whose values are ORed (naming both *widens*), and `lead_department` has no source field on a lead row so no vocabulary could ever grow for it. The headcount band (`Campaign.headcount_min/max`) rides every node unchanged and is never searched. **A node's value is arithmetic over labels, and no model is involved**: `P̂(node) = (a + 2·P̂(parent)) / (a + b + 2)`, where `a`/`b` are the qualified/rejected leads whose `profile_text` contains all of the node's tokens — Laplace smoothing pointed at the **parent's rate** rather than at 0.5, so the parent supplies the level and the child's own counts move it off. **The `LabelStore` counts the campaign's anchors as positives**, and that is what makes the cold phase work at all: expansion only offers a token that has shared a *qualified* profile with the node, so a campaign that has never accepted anybody had no qualified profile, could not grow past its one-token seed nodes, fired queries too broad to qualify anyone, and therefore still had no qualified profile — a closed loop in which the seed's own tokens could never be conjoined into the precise query the walk exists to find. The synthetic ideal profiles are written in `profile_text`'s shape, so they tokenize like any lead and say which words describe the people this campaign wants — the same bargain the GP already takes, on the same evidence: `BayesianQualifier` keeps the anchor profiles permanently, so `Campaign.anchor_profiles` is a fixed set once written and this store needs no phase check to read it. They deliberately do **not** feed the vocabulary: an anchor is one flat string with no per-field structure, and splitting it by guess would file `united states` as a job title. Anchors say which words go *together*; only a real lead row says which field a word is searchable in. Selection draws `θ ~ Beta(a + 2·P̂(parent), b + 2·(1 − P̂(parent)))` per frontier node and fires the argmax (Thompson, but the Beta params *are* the estimate — one line, nothing to tune; `select.THOMPSON = False` gives greedy). **The GP no longer selects queries**: measured on ~4,100 parent→child edges with the GP fit on half the labels and every truth on the other half, counting wins outright (pearson 0.661 vs 0.450) and the GP adds nothing on top (0.660); residual anchoring is worth 0.02 at λ≈0.15 and is *worse than nothing* at λ=1. The GP stays the qualifier — it produces the `a`/`b` the walk counts. `core/pipeline/`: `icp.py` (the two cold-start priors from the same inputs — `generate_seed`: one LLM pass → the opening **keywords** + size band, the *only* LLM call discovery makes about queries, with the spec's phrases **split into single-word tokens** so `"Head of Growth"` becomes three separate one-token nodes rather than one near-empty three-token AND; `generate_anchors`/`ensure_anchors`: the ICP as synthetic ideal *profiles*, embedded as the GP's positives so a campaign whose every verdict is a rejection can fit at all — profiles not product prose because the space is one of lead embeddings, kept permanently once written), `vocabulary.py` (**growth is counting, not generation**: the vocabulary is the words appearing in profiles the LLM already accepted, one word per keyword, admitted at **df ≥ 2** — a floor that drops 65% of the vocabulary and loses *zero* good tokens, while removing a singleton tail that is mostly company names and would otherwise be 56% of the top of any embedding ranking. Runs every pass; no cadence knob, no high-water mark. A token's field is read from the row fields that *are* that axis (`discovery.KEYWORD_SOURCE_FIELDS` → `Lead.source_fields`) — **`lead_job_title` reads `contact_job_title` only**, never the headline, whose marketing prose (`user`, `agents`, `shipping`, `ai-powered`) cleared the df floor and got filed as job titles, keeping the per-field vocabularies nearly disjoint; `lead_seniority` is seeded whole from the provider's closed 12-value list and never grown), `select.py` (**the selector, and it is arithmetic**: `LabelStore` (token sets + verdicts, loaded once per pass — hundreds of rows, so counting a node is a microsecond set-containment scan), `estimate`, `frontier`/`next_node` (one pool: deepening a vein and opening a fresh node are two rows scored the same way, not two policies needing an alternation rule), `expand` (children are the node plus one token that has shared a **qualified** profile with it — which bounds the frontier without a top-K cap and keeps every child a proposition the evidence can speak to), `seed_frontier` (no root: one depth-1 node per keyword, and the empty query is never fired since it matches everyone and its 10k window is the provider's famous-company head), `advance`/`retire`/`token_key`), `discover.py` (`discover(campaign, qualifier)`: ensure vocabulary + frontier → draw a node → page it → harvest and expand, or classify the empty page and retire, then try the next node; `qualifier` is accepted and ignored). **Retirement is a corpus fact, never a model fact** — nothing is retired for scoring badly, only for emptiness, and *which* emptiness depends on the offset because the provider answers `0` for all of them: **offset 0** = the index matches nobody → `dead`, subtree pruned (a superset matches a subset of people); **below the 10k reach cap** = the vein drained → `drained`, subtree pruned too (every match is already a `Lead` here); **at the cap** = Elasticsearch's `max_result_window`, not the end of the population → `drained` but the **subtree stays**, since adding a token opens a fresh window. The fourth case is not an answer: rows empty while `summary.leads_found` is positive is a **transport artifact** (a burst answered a 71M-lead query with an empty page in 0.0s) and never retires anything — `search()` returns `Page(leads, leads_found)` and the count is trusted **only at offset 0**. Then `qualify.py` (`run_qualification` — the balance-driven pick, which on a cold campaign runs against the anchored GP rather than against no model at all) → `ready_pool.py` (GP gate; `min_gp_confidence` is the paid-lookup spend gate **and nothing else**) → `top_up.py` (**one** unit of work per call — the cycle is the loop that used to live here. `top_up` is the *labelling* steering, the qualifier's own **explore/exploit** split: **cold phase** (`is_cold` — `n_real_positives < ANCHOR_COUNT`, a clock independent of whether the anchors themselves are still standing) does **both** moves every pass — one query in, one label out — because rankings still lean on the anchors' guess, so no observed signal says a label beats a page; discovery's return is ignored, so only an empty pool stalls. The anchors are permanent — `set_anchors`/`update` never trim them — so what ends the cold phase is real acceptances reaching `ANCHOR_COUNT`, not the anchors running out. *(Discovery itself no longer has a cold phase — every node is scored the same way from day one, with the label store's base rate standing in for the level a root would supply.)* **the cold phase always exploits** — while real positives are still short of `ANCHOR_COUNT` the one goal is *more real positives*, and the highest-P lead is the one most like the ideal profile, where BALD spends each call on the lead the model is most *confused* about, i.e. the one least like the ICP; the balance could not have chosen it anyway, since while `is_cold` held, `n_neg > n_pos` was false by construction. Once real positives reach `ANCHOR_COUNT` the phase ends and balancing (`_balance`) takes over — the anchors keep contributing to every fit after that too, a small constant addition next to a growing real count. Past the phase: **explore** (`neg ≤ pos`) BALD-labels the pool with **no gate**, **exploit** (`neg > pos`) qualifies the strongest lead clearing `min_gp_confidence` or `discover`s if none clears it). **Keyword injection survives but is vestigial**: a discovered lead is still embedded as `profile_text + keyword_terms(its retrieving node)` while `profile_text` (the LLM qualifier's input) stays clean — its original job was letting the GP score a never-run query by its keywords, and what keeps it now is only that every cached `Lead.embedding` was built that way. See the roadmap card `p1-e3-leadfinder-index-semantics-and-query-model-rethink` (supersedes `p2-e3-discovery-unified-gp-query-selection` and `p2-e3-discovery-empty-set-backoff`).
- **The lead export**: `core/export.py`, printed by `find` — the finder's **public output**, and Tier 0 of the boundary described by the `openoutreach-docs` card `p1-e3-leadfinder-sequencer-boundary`. The governing rule is that **our own sender gets no privileged path**: a sequencer, a CRM and a spreadsheet all read the same rows. **The column names are the importers', not ours** — Instantly and Smartlead both *require* `email`/`first_name`/`last_name` and recognise `company`/`title`/`website`/`linkedin_url`, mapping anything else to a custom variable, so the record is exactly `email, first_name, last_name, company, title, website, linkedin_url, reason, lead_id, qualified_at` and a file imports without column mapping. `qualified_at` (`Deal.creation_date`, ISO 8601) is provenance the file keeps — a caller tells which rows its own call produced by comparing against its start time, and a sequencer imports only what is newer than last time; a `new` flag would be invocation-relative state in a file that outlives the invocation, and therefore a lie the second time it is read. The internal model keeps its own names (`profile_url` is provider-agnostic on purpose; a `domain` is not a `website`) and `lead_record()` is the one translation — one schema cannot match N importers, so the mapping is a function, never a migration. **One record, two serialisations**: `JSON_FIELDS` is the record — those ten plus `profile_text`, the raw firmographic string the qualifier judged on — and `RECORD_FIELDS` is the importer-shaped **projection** of it, so `write_csv` projects rather than defining a second schema (`None` → empty cell; `profile_text` is `""`, never absent). `--json` is **JSON Lines** — one record per line on stdout, run metadata as one JSON object on stderr and nothing else there (no banner, no logs), because a truncated stream stays usable and a caller should not need `tail -1` over prose. **Output is progressive by default** (either format): `find` writes what the campaign already has immediately, before any work, then writes each new lead's record the moment its deal settles — `find 20 emails | outsend` starts feeding the sender within seconds of the first resolved address instead of after the whole run. It rides the same `on_new_lead` hook `--open` already used (`_combine` in `find.py` chains the two, via `core/export.py:IncrementalWriter`, which owns the CSV-header-on-first-row/JSON-line timing and flushes after every write). `--new` skips the opening bulk and only ever streams what this run produces. `--batch` is the escape hatch back to the old shape — nothing is written until the job ends, then the whole thing prints once, for a consumer that cannot take a partial stream. This is safe where a daemon-managed live CSV was not: that file was deleted because rows kept changing state under an unbounded process running for days; a single `find` run's deals settle once and stay settled for the rest of that run. **Summarising for a message is the sender's job**: `profile_text` crosses raw and the receiver extracts what an opener needs, which is why `core/db/summaries.py`, `Deal.profile_summary` and the vendored mem0 are gone — they had no consumer here once the sending leg left. `reason` is **operator-facing** evidence, never text for the prospect. The compatibility rule replaces the shared schema package we are not building: a receiver ignores unknown keys, and this side only ever adds. **There is no score column and the export touches nothing but the DB** — exporting the GP posterior was a category error (`min_gp_confidence` is the paid-lookup *spend* gate and nothing else; the fit verdict is the LLM's, already present as `reason`), and it cost an O(n³) `qualifier_for` fit — minutes on the live 2,538-deal campaign — which also calls `ensure_anchors`, so a cold campaign would have spent LLM calls and mutated state from a read-only command. The **Deal** is the unit (the `reason` is per-campaign). **A Deal is not an endorsement**: `DealState.FAILED` (the LLM's campaign-scoped rejection) and `Lead.disqualified` (the permanent opt-out) are *different columns*, and the first shipped version filtered only the second — exporting 1,944 rows whose `reason` read "does not align well with the target market". Both are excluded, always, with no flag to include them. **There is no command and no file — it is `find`'s stdout**, and the whole campaign every time, so `> leads.csv` is correct by construction (the newest file supersedes every earlier one, and a lead whose address resolved since last time comes back with it filled in). It is one file to overwrite, not a batch per run; `--new` narrows to this run's rows, `find 0` prints without working. This took two attempts in one day: a command nobody discovered → a CSV the daemon kept current (naming rule, collision tie-break, rewrite-vs-append, atomic temp-and-rename) → nothing at all. **Every one of those problems existed only because a background process can change a row after it was written.** **The boundary is one-way** (2026-08-19): leads leave, nothing comes back. There is no inbound endpoint and no event vocabulary — reply outcomes are conversation states belonging to whoever sent the mail, and a finder that never contacts anyone is not the sender under CAN-SPAM/GDPR, so suppression stays with the sequencer (Instantly and Smartlead both block a suppressed address at import). The GP therefore keeps training on the LLM's fit verdict alone; `get_labeled_arrays` has never seen a market signal, so nothing was lost. `lead_id` keeps the door open if that is revisited — the one candidate is `bounced`, which grades the row we emitted rather than the message. Import dedupe is **opt-in** on Smartlead and undocumented on Instantly, so every adapter's docs must tell the operator to enable it.
- **Lead identity + Company**: `Lead.full_name`/`first_name`/`last_name`/`job_title` (all nullable — `NULL` means the provider never told us) and `Lead.company` → `crm.Company`, a shared employer row keyed on `Company.key` (the lowercased domain, or `name:<name>` when no domain was reported). They serve the export and the record the product keeps, and are deliberately **out of** `profile_text` and the embedding: a name carries no ICP signal and would only give the GP noise. **Nothing splits a name in-house** — discovery reports one `contact_full_name`, and the paid enrichment response reports the real `contact_first_name`/`contact_last_name` at no extra call or credit (`enrichment/lookup.py` writes them on a hit). A hub-cache resolution never reaches that provider, so its name parts stay `NULL`; they feed a sequencer's `{{first_name}}` merge tag, where a guess lands in someone's cold email. The **enrichment query stays URL-only** by decision — the provider accepts name/company and resolves better with them, but the less of a lead's record leaves for a third party the better, and URL-only measures ~42% usable. `Company` rows are *what the provider said*, not verified truth (Lead Finder fuzzy-matches them), and a firm seen once with and once without a domain produces two rows — a known cost of the simple key.
- **Contacts store (hub)**: `contacts/service.py` — an optional free `profile_url → email` cache at `hub.openoutreach.app`, tried *before* the paid finder and given back to on a fresh paid hit. Both calls are best-effort (outage/no-token → no-op). The give-back is **non-EEA only** and derived from the operator's onboarding country (`not is_eea_located`) — never a stored toggle; the server re-gates authoritatively. **Identity is minted at onboarding, not earned by contributing** (`register_operator`, called from `_finalize_account`): the token says *which install this is*, the balance says what it may read, and folding them into one act meant an install that cannot contribute had no identity at all and stayed invisible to the hub for life. It is minted from the email onboarding already collects — no new question — **regardless of jurisdiction**, since the EEA/UK/CH rule governs *contributing records*, a different act still gated in `contribute`. Best-effort and idempotent; `_register` remains as the folded-into-a-contribution path for a hub that still requires a record. The token is stored in `SiteConfig.contacts_api_token` (never the repo). **The give-to-get balance is visible in `status`, as its own `hub` key** — a different number on a different service than the `credits` key (BetterContact's own prepaid balance); `hub_balance()` reads it via a spend-free record-less `register` call, and `known: False` (no token, or an outage) must render as *unknown*, never as a balance of zero. A `resolve` miss also tells the two zeros apart: `credits <= 0` logs as *no balance* (the store was never even checked — `resolve_lead` short-circuits at zero balance server-side), anything else logs as *no stored email*. **Not marketing consent** — the newsletter opt-in is that, and it is jurisdiction-aware. **Tests may never reach either service**: `tests/conftest.py::_no_live_writes_to_our_own_services` refuses `contacts.service` and `core.newsletter` POSTs, because completing onboarding in a test would otherwise register a fake operator against production and sign a fake address up to the list.
- **Config**: `SiteConfig` DB singleton — `ai_model` (a pydantic-ai `provider:model` id, e.g. `anthropic:claude-sonnet-4-5-20250929`; bare `gpt-*`/`o1`/`o3`/`claude-*`/`gemini-*` auto-prefixed), `llm_api_key`, `llm_api_base` (only for `openai_compatible:*`), `bettercontact_api_key` (blank disables discovery + enrichment), `contacts_api_token`/`contacts_api_url`, `country_code` (the only persisted operator setting — drives the email jurisdiction rules). `core/conf.py`: `CAMPAIGN_CONFIG` (ML defaults, incl. `min_gp_confidence` for the paid-step rank gate — which is **only** a spend gate; there is no discovery-interleave threshold and **no discovery cadence knob**, since growing the vocabulary is now a tokenize-and-count that runs every pass rather than an LLM call worth rationing), `COLLECT_BACKOFF_BASE_S`/`COLLECT_BACKOFF_MAX_S` (the lookup poll backoff — doubling, no deadline, MAX rails the interval only), `CYCLE_SECONDS` in `core/cycle.py`. **There is no spend cap on the paid lookup**: it used to ride on send headroom, and with no sending leg nothing replaced it — what bounds the spend is the operator's prepaid provider balance, which we cannot see. *(Gone with the sending leg: `WARM_*`, `MIN_SEND_INTERVAL_SECONDS`/`SEND_INTERVAL_JITTER_*`, `SEND_WINDOW_*`, `COLLECT_TODAY_HORIZON_S`, `MAIL_PASS_INTERVAL_S`.)* `core/business_time.py` has **no knob** and only *measures* (Mon–Fri, no public holidays); with the agent gone the pipeline no longer calls it.
- **Django apps** (nested under `openoutreach/`, dotted `AppConfig.name`, short labels): **just two** — `core` (engine — the cycle, operator lookup, Campaign/SiteConfig, llm, onboarding, ML, discovery/qualify pipeline, the lead export) and `crm` (Lead + Company + Deal). `enrichment` and `contacts` are service-only modules (no models, not installed apps). *(`emails`, `chat` and `legacy` are gone — see* The cut *above.)*
- **State dir**: everything the operator's install writes hangs off one root, `settings.state_dir()` — **the checkout when `manage.py` sits beside the package, otherwise `~/.openoutreach`**, because from a wheel `ROOT_DIR` is site-packages and neither a CRM nor a model download belongs there. Two things live under it: `data/db.sqlite3` and `.cache/fastembed` (65 MB of ONNX weights, ~11 s on a cold machine). **The cache is deliberately not derived from the database path** — `--db /tmp/scratch.sqlite3` must not send fastembed off to re-download beside a throwaway DB. The Docker image names the DB outright (`OPENOUTREACH_DB=/app/data/db.sqlite3`) and mounts a volume at `/app/data`. Any command takes a global `--db PATH` (or `OPENOUTREACH_DB=…`) to run against a different SQLite file; `settings.py` creates the parent dir if needed. SQLite runs in **WAL** so a second process (`status`) can read while a job writes.
- **A fresh install is an answer, not a traceback**: `settings.py` creates the *directory*, but only `run` migrates, so every other verb used to hit a raw `no such table: core_campaign`. `OpenOutreachCommand.requires_database` (default `True`, `False` on `run`) guards it in `execute()` — after argument parsing, so `--help` still answers — and reports `error: not_initialized: …` naming the DB path. Reporting zero campaigns instead would be exactly the empty-result failure the vocabulary exists to prevent. **One more failure that was shaped like a bug**: `verify_llm_credentials` caught `Exception`, so a `TypeError` from a library major (`anthropic` 1.0.0 dropping `temperature`) came back as `bad_config: OPENOUTREACH_LLM_API_KEY` and sent the operator after a key that was fine. It now catches only what a configuration causes (`ModelAPIError`, `UserError`, `ValueError`) and lets a bug keep its traceback.
- **Docker**: `python:3.12-slim`, two stages — a venv at `/opt/venv` holding the installed package, copied wholesale into a runtime that carries neither `git` nor `uv`. No browser, no VNC. `compose/openoutreach/Dockerfile`. **Server deploy only**: no `BUILD_ENV`, no dev extras, no tests in the image, and the compose file mounts only `./data` (the code is what the image was built from).
- **CI/CD**: `.github/workflows/tests.yml` (native pytest on 3.12), `deploy.yml` (**every push to `main`**, plus `v*` tags → tests → build + push `ghcr.io/eracle/openoutreach` tagged `latest` + `sha-<pushed tip>` → `repository-dispatch: image-updated` to the hub repo). **Every green push to `main` also publishes a new version to PyPI** via trusted publishing (`publish-pypi`, environment `pypi` — the trusted publisher is registered against that workflow *filename* and that environment name, so neither may be renamed, and the environment must carry **no required reviewer** or every push would wait on a click). **The version is derived, never committed**: `pyproject.toml`'s `version` is the *base* (major.minor, bumped by hand), and the patch is `git rev-list --count v0.1.0..HEAD` at publish time — hence `fetch-depth: 0`, since a shallow clone cannot count. `skip-existing` makes a re-run a no-op. **Tags no longer publish** — they remain human markers, and the image job still reads them for semver tags. **This replaced tag-gated releases on 2026-08-22**: `v0.1.0` was tagged by hand and then twelve commits of first-run work landed behind it while `uvx openoutreach` served the version from before all of them, so a release nobody has to remember cannot drift. The trade is knowing and accepted — **there is now no release gate on either artifact**, so code *and schema migrations* reach anyone pulling `latest` or installing the package on merge, and `needs: test` is the whole gate.
